# Руководство для соавторов

Привет! Прочти этот документ перед тем, как начнёшь писать код — он объясняет, как устроен проект, как подготовить окружение и как сделать так, чтобы твой PR влился быстро и без боли.

Философия проекта простая: **ядро парсера стабильно, всё остальное — конфигурация и расширения**. Поэтому большинство изменений вливаются маленькими, понятными PR.

---

## 1. Подготовка окружения

Требования: **Python 3.11+**, `git`, для Docker-запуска — `docker` (или podman).

```bash
# 1. Клонируй репозиторий
git clone git@github.com:Yartron/parser_avito.git
cd parser_avito

# 2. Создай виртуальное окружение и зависимости одной командой
make venv
# если несколько версий Python и нужна конкретная (3.11+):
make venv PYTHON=python3.12

# или вручную
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt pytest ruff

# 3. Проверь, что всё работает
make test   # pytest — все тесты зелёные
make lint   # ruff check . — линтер зелёный
```

Если `make` недоступен (Windows без build tools) — см. [Makefile](Makefile): это просто обёртки над `python -m pytest -v` и `ruff check .`.

## 3. Секретные данные: config.toml и .env

❗ **Никогда не коммить токены, ключи, прокси с логином/паролем.**

Разделение источников (приоритет сверху вниз):

1. **Переменные окружения** (`export`, `docker run -e ...`) — высший приоритет
2. **`.env` файл** в корне (создаётся из `.env.example`, в git не попадает)
3. **`config.toml`** — остаётся дефолтным источником

Что можно переопределять через окружение: `TG_TOKEN`, `TG_CHAT_ID`, `VK_TOKEN`, `VK_ID` (= `VK_USER_ID`), `COOKIES_API_KEY`, `PROXY_STRING`, `PROXY_CHANGE_URL`, `PROXY_NOTIFIER`. Полный список с комментариями — [.env.example](.env.example).

Правила:
- значения реальных секретов — только в `.env` (локально) или переменных окружения (сервер/Docker);
- в issue и PR выкладывай конфиг **только замаскированным**;
- если секрет всё же утёк в коммит — считается скомпрометированным: отзови токен и сообщи мейнтейнеру (git history чистить бессмысленно).

## 4. Процесс работы

### 4.1 С чего начать

Сначала **issue**:
- любая идея/багфикс — опиши в issue, там наберётся контекст и список репродукции;
- если изменение большое (ядро, алгоритм парсинга, зависимости, версии Python) — issue обязателен **до** написания кода. Это единственный способ не сделать работу впустую.

### 4.2 Ветки

Названия: `<тип>/<краткое описание>`, желательно с issue-номером:

```
feat/#300-incremental-save
fix/#312-excel-crash
docs/ci-docs
chore/ruff-config
deps/flet-update
```

| Тип | Смысл |
|---|---|
| `feat` | новая функция |
| `fix` | исправление бага |
| `docs` | только документация |
| `chore` | конфиги, линтер, CI |
| `deps` | обновление зависимостей (в т.ч. Dependabot) |

### 4.3 Коммиты

Формат — гибкий conventional: `<тип>: <что сделал> (#issue)`

```
fix: save results incrementally per page (#300)
feat: VK уведомления с картинками
docs: описан CI/CD pipeline
```

- один PR — одна смысловая единица;
- не смешивай форматирование и логику в одном коммите;
- можешь коммитить как удобно в своей ветке, но перед PR полезно сделать `git rebase -i` и почистить.

### 4.4 Pull Request

1. PR идёт в ветку `master`.
2. Перед PR прогони: `make lint && make test`.
3. CI (`ci.yml`) обязателен к «зелёному»: линтер ruff + тесты на Python 3.11/3.12 + сборка Docker-образа.
4. Заполни шаблон PR (появляется при создании) — чек-лист там короткий и честный.
5. Ревью: мейнтейнер отвечает обычно в течение пары дней. Что проверяется:
   - соответствует ли изменение концепции «конфигурация вместо ядра»;
   - нет ли в `save()` сетевых запросов, глобального состояния в `Notifier` и т.д. (см. [docs/DOCS.md](docs/DOCS.md));
   - покрыто ли тестами;
   - не затащены ли секреты в код/конфиг.
6. Хочешь обновить свою ветку с master — используй `git rebase master` (PR не «разбухает» от merge-коммитов).
7. PR вливается squash-мержем или merge-коммитом — на усмотрение мейнтейнера.

### 4.5 Рабочий цикл (шпаргалка)

```bash
git switch -c fix/#300-incremental-save     # ветка от master
# ... код ...
make lint && make test                      # локальная проверка
git add -p && git commit -m "fix: ..."      # точечные коммиты
git push -u origin fix/#300-incremental-save
# открыл PR на github, дальше ревью + зелёный CI
```

## 5. Тесты и качество

- Настройки линтера — в `ruff.toml` в корне: набор `E4/E7/E9/F` (ловим реальные ошибки, без стилистических придирок), star-импорты локализации (`from lang import *`) разрешены.
- Тесты: `pytest` + `pytest.ini` (`pythonpath = .`). Пиши быстрые юнит-тесты без сети; mocks для HTTP. Примеры смотри в `tests/`.
- Если ты добавил настройку в `config.toml` — проверь, что тесты, `dto.py` (`AvitoConfig`) и GUI согласованны (старые параметры конфига «переживаются» за счёт фильтрации по полям dataclass).
- Новая логика в `load_config.py`/`utils/env_loader.py` обязана иметь тесты (см. `tests/test_env_loader.py`).

## 6. Релизы (для мейнтейнеров)

Релизный процесс описан в [docs/CI.md](docs/CI.md). Кратко:

1. Обнови `docs/CHANGELOG.md` и `version.py` (`VERSION = "x.y.z"`) — PR'ом `feat/x.y.z version`.
2. Merge в `master` → workflow `release.yml` соберёт Windows `.exe` и создаст GitHub Release.
3. `git tag vX.Y.Z && git push origin vX.Y.Z` → workflow `docker.yml` соберёт и опубликует Docker-образ `ghcr.io/<owner>/parser_avito:x.y.z`.
